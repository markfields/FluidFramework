Fluid Container Runtime Collaboration DSL

A source-grounded, typed language for describing multi-client Fluid scenarios across Loader, Container Runtime, operations, summaries, snapshots, loading groups, and pending-state rehydration.

This guide assumes familiarity with Fluid Framework concepts. It does not assume prior experience designing or using domain-specific languages.

Status and purpose

Artifact Internal TypeScript DSL compiled by the normal TypeScript compiler.
Output A pure, JSON-serializable scenario intermediate representation.
Validation Domain-level identifier, lifecycle, provenance, and option checks.
Proof Ten existing end-to-end tests restated in the language.

The implementation is a descriptive proof of concept. It records what a collaboration scenario means and validates whether that description is representable. It does not yet execute the scenario against ITestObjectProvider.

Important: the validator is not a fake ordering service or a fake Container Runtime. Expected observations remain explicit in the scenario. The validator checks that referenced clients, operations, summaries, snapshots, and captured states exist and that commands obey known lifecycle guards.

DSL primer

What is a DSL?

A domain-specific language is a deliberately small language for one problem domain. SQL describes queries. Mermaid describes diagrams. This DSL describes Fluid collaboration scenarios.

A general TypeScript test can express almost anything. That flexibility creates incidental choices: loaders, callbacks, event wiring, queue timing, test harness helpers, and assertions can all be arranged in many ways. A DSL removes most of those choices and leaves a constrained vocabulary:

load attach disconnect submit operation synchronize summarize acknowledge summary capture pending state rehydrate expect

Why an internal DSL?

This is an internal DSL: TypeScript supplies the parser, module system, editor support, and type checker. There is no custom lexer or text parser. Progressive interfaces constrain which methods are legal at each point in the builder.

scenario name→source test→ document→clients→ coverage→steps

Three layers

Layer Responsibility File
Fluent grammar Readable authoring surface and compile-time ordering. builder.ts
Semantic model Pure commands, controls, expectations, and metadata. model.ts
Domain validator Deterministic errors phrased in Fluid concepts. validator.ts

Design lineage: Fowler and Tickloom

Martin Fowler's LLMs and DSLs article argues that a small language plus a deterministic validator narrows the space in which an LLM can make mistakes. The durable artifact becomes the domain program, not the prompt that generated it.

Tickloom demonstrates this with an internal Java DSL for distributed-system scenarios. Its strongest transferable ideas are:

  • progressive interfaces for grammar;
  • a semantic model separate from fluent syntax;
  • domain-level validation and execution;
  • scenario artifacts that are readable enough to maintain directly.

This Fluid design also corrects several Tickloom sharp edges:

  • Each client scope is immutable; selecting Bob cannot change an earlier Alice scope.
  • Commands are inspectable records, not anonymous execution lambdas.
  • Persistent effects use honest verbs such as pause, resume, disconnect, and connect.
  • Identifiers and artifact provenance are validated before any future execution.

Scope and abstraction boundaries

In scope

  • container creation, attach, load, connect, disconnect, close;
  • intermediate connection states and requested connection mode;
  • DataStore creation, visibility, lazy realization, and opaque operations;
  • outbound batching and op virtualization;
  • sequencing, pending state, replay, resubmission, and local acknowledgement;
  • summary generation, upload stage, broadcast, ack/nack, and handle reuse;
  • snapshot selection, refresh, and loading-group fetches;
  • ordinary pending-local-state capture and self-contained full-container capture;
  • frozen/offline writable load and later online resume.

Out of scope

  • DDS-specific operation semantics;
  • concrete driver implementations, endpoint names, token shapes, or cache internals;
  • a simulated ordering service or storage service;
  • automatic proof that an expectation is behaviorally true;
  • full GC, aliasing, staging mode, and signal APIs in the first prototype.
The DataStore/DDS boundary is intentional. A scenario may say that operation offline-3 targets DataStore root, but it does not say whether that operation is a map set, counter increment, tree edit, or sequence change.

Fluid architecture represented by the language

Load pipeline

resolve URL→create document service→ connect storage→fetch snapshot/version→ initialize protocol→instantiate runtime→ replay saved/stashed ops→connect and catch up

Outbound operation pipeline

opaque DataStore op→ContainerRuntime submit→ Outbox batch→group→ compress→chunk→ Loader submitBatch→ordering service

Pending state stores the original unvirtualized runtime operations, including batch information and local metadata. That is why replay expectations use logical batch and operation identifiers rather than wire chunks.

Inbound operation pipeline

sequenced message→unchunk→ decompress→ungroup→ pending-state reconciliation→ ContainerRuntime dispatch→ ChannelCollection→DataStore

Summary pipeline

base validation→generate tree→ upload with context→submit summary op→ broadcast→ack or nack→ refresh tracked state/snapshot

States and transitions

Attach state

State Meaning Important transition
detached No service document yet. beginAttach or successful atomic attach.
attaching Create/attach is in progress. May be serialized; later completion becomes attached.
attached Backed by a service document or rehydrated attaching state. May connect, submit runtime ops, summarize, and capture pending state.

Serialization provenance matters: rehydrating state serialized while detached produces a detached container, while rehydrating state serialized while attaching produces an attached container.

Connection state is not connection mode

Axis Values Why separate?
Connection state Disconnected, EstablishingConnection, CatchingUp, Connected Describes Loader connection/catch-up lifecycle.
Mode read, write A connected read client is not write-capable.
Read-only true, false Public/runtime read-only state is not identical to transport mode.
Environment none, service, frozen A writable frozen container can be logically connected without live driver wiring.

Operation states

The prototype uses expectation vocabulary rather than attempting a full simulator: pending, sequenced, processed, acked, and notProcessed.

Summary states and stages

Stages describe an attempt: base → generate → upload → submit. States describe its protocol lifecycle: local → broadcast → acked or nacked.

Captured state artifacts

Artifact Produced by Use
pendingLocalState IContainer.getPendingLocalState() Online resume with base snapshot, saved ops, and stashed runtime state.
fullContainerState captureFullContainerState() Self-contained frozen/offline load, including required attachment content.

These are not two modes of the same runtime method. They are separate current APIs with different guarantees. Full-container capture does not currently support loading groups.

Language grammar

Top-level form

fluidScenario("scenario name")
  .fromTest({
    file: "packages/test/test-end-to-end-tests/src/test/example.spec.ts",
    suite: "Suite name",
    test: "Test name",
  })
  .document(document("logical-document", dataStores, runtimeOptions))
  .clients(
    interactiveClient("alice"),
    summarizerClient("summarizer"),
  )
  .covers("op-stream", "summarization")
  .steps((s) => {
    // Scenario timeline
  });

Scopes

Scope Examples Semantic owner
s.client(id) load, attach, submit, summarize, capture, realize, close Container/ContainerRuntime instance
s.processing(id) pause or resume inbound/outbound processing Test-harness queue control
s.service() synchronize, summary ack/nack, full-container capture Abstract service/driver boundary
s.expect… client, op, batch, summary, snapshot, sequence, DataStore Observation recorded in the IR

Immutable client scopes

const alice = s.client("alice");
const bob = s.client("bob");

alice.disconnect();
bob.submitOperation({ id: "op-1", dataStore: "root" });
alice.connect();

alice remains bound to Alice. Selecting Bob cannot mutate it. This avoids the shared-current-client bug identified in Tickloom's current builder.

Semantic model

Every fluent call appends a plain-data step. There are only three top-level step kinds:

  • command — an action or control stimulus;
  • expectation — an observation the future executor must check;
  • note — explanatory intent retained with the scenario.
{
  "kind": "command",
  "command": {
    "kind": "submitBatch",
    "client": "writer",
    "batch": {
      "id": "large-batch",
      "operations": [
        { "id": "large-op-0", "dataStore": "root", "sizeInBytes": 100 }
      ]
    }
  }
}

Because the IR contains no closures, loaders, containers, driver objects, or test provider instances, it can be serialized, diffed, rendered, analyzed, or consumed by a later executor.

Deterministic domain validator

The validator currently checks:

  • unique client, DataStore, operation, batch, summary, snapshot, and capture IDs;
  • all references point to previously declared or produced artifacts;
  • load, attach, connect, disconnect, close, submit, summarize, and capture guards;
  • serialized detached/attaching provenance;
  • frozen load requires captureFullContainerState output;
  • compression requires grouped batching;
  • chunking requires compression;
  • loading groups require data virtualization;
  • writable frozen flow requires turn-based flush, grouped batching, and batch IDs;
  • full-container capture and loading groups are currently incompatible.

Example error

steps[2]: Client 'alice' cannot submit runtime operations while detached.
clients: Client 'alice' is declared more than once.

These errors are intentionally expressed in domain vocabulary rather than as a null dereference or a test-harness stack trace.

Worked example: disconnect gates inbound processing

export const disconnectGatesInboundOps = fluidScenario(
  "disconnect gates inbound operation processing",
)
  .fromTest({
    file: "packages/test/test-end-to-end-tests/src/test/container.spec.ts",
    suite: "Container",
    test: "can control op processing with connect() and disconnect()",
  })
  .document(document("collaboration", [{ id: "root", root: true }]))
  .clients(interactiveClient("writer"), interactiveClient("reader"))
  .covers("container-lifecycle", "op-stream")
  .steps((s) => {
    s.client("writer").load({ from: { kind: "service" } });
    s.client("reader").load({ from: { kind: "service" } });

    s.client("writer").submitOperation({
      id: "initial-value",
      dataStore: "root",
    });
    s.service().synchronize();
    s.expectOperation("initial-value").at("reader").toBe("processed");

    s.client("reader").disconnect();
    s.client("writer").submitOperation({
      id: "while-disconnected",
      dataStore: "root",
    });
    s.service().synchronize("writer");
    s.expectOperation("while-disconnected")
      .at("reader")
      .toBe("notProcessed");

    s.client("reader").connect();
    s.service().synchronize();
    s.expectOperation("while-disconnected")
      .at("reader")
      .toBe("processed");
  });

What disappeared from the original test?

  • runtime factory construction;
  • provider plumbing;
  • entry-point casts;
  • DDS event and timeout wiring;
  • DDS value details.

What remains is the architectural intent: two clients, a disconnection boundary, an op submitted while disconnected, and catch-up after reconnect.

Extending the language

  1. Start with the semantic model. Add a serializable command or expectation to model.ts.
  2. Add the narrowest fluent verb. Put it on the correct immutable scope in builder.ts.
  3. Add domain validation. Validate references, artifact provenance, and known lifecycle guards in validator.ts.
  4. Ground it in a real test. Add a source-traceable scenario and a negative validator test.
  5. Update this guide.

Candidate next surfaces

  • staging-mode enter/commit/discard;
  • signals, explicitly separated from persisted/replayed ops;
  • summary nack, retry, and timeout outcomes;
  • alias success/conflict/already-aliased transitions;
  • saved-op replay versus stashed-op application as explicit events;
  • blob upload/attach pending states;
  • driver error category and retry metadata;
  • rendering the IR as Mermaid sequence/state diagrams.

Future executor architecture

A future runner should consume the IR through adapters rather than adding Fluid objects to the semantic model.

FluidScenario IR→harness adapter→ ITestObjectProvider+IOpProcessingController+ summary helpers→observations

Likely adapter responsibilities

  • map logical clients to real containers and entry points;
  • map opaque DataStore operations to a minimal test DataStore op source;
  • pause/resume/process inbound and outbound queues;
  • run synchronization barriers;
  • invoke summarizer helpers and observe summary ops/acks;
  • wrap storage interfaces to count snapshot fetches;
  • capture and reload pending/full state artifacts;
  • evaluate expectation records and produce domain-level failures.
The semantic model is already executor-ready: commands and expectations are serializable discriminated unions, client IDs are stable, and artifacts have explicit provenance.

Glossary

Internal DSL
A domain language expressed through the syntax and type system of a host language.
Semantic model / IR
The plain-data representation produced by the fluent syntax.
Progressive interface
A builder interface that returns a narrower next interface, making invalid method orderings fail to compile.
Artifact provenance
Information about how a snapshot or pending state was produced, used to validate legal future transitions.
Op virtualization
Container Runtime transformations that group, compress, and chunk logical runtime operations for transport, then reverse those transforms inbound.
Data virtualization
Lazy loading of DataStore snapshot content by loadingGroupId. It is distinct from op virtualization.
Saved op
A sequenced op after the base snapshot, replayed during pending-state load.
Stashed op
A local pending op applied at its original reference sequence and later resubmitted/reconciled.
