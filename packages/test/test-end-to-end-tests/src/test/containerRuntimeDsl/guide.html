Fluid Container Runtime Collaboration DSL

A source-grounded, typed language for describing multi-client Fluid scenarios across Loader, Container Runtime, operations, summaries, snapshots, loading groups, and pending-state rehydration.

This guide assumes familiarity with Fluid Framework concepts. It does not assume prior experience designing or using domain-specific languages.

Status and purpose

Artifact Internal TypeScript DSL compiled by the normal TypeScript compiler.
Output A pure, JSON-serializable scenario intermediate representation.
Validation A proof-of-concept validator currently combines structural and semantic checks.
Proof Ten existing end-to-end tests restated in the language.

The implementation is a descriptive proof of concept. It records what a collaboration scenario means and validates whether that description is representable and internally consistent. It does not yet execute the scenario against ITestObjectProvider.

This guide is the conceptual introduction. The adjacent DEV.md is the authoritative maintainer specification for validation ownership, test conversion, language-extension gates, and the aspirational backlog.

The boundary that matters: the DSL declares the sequenced trace; it does not decide it. There is no simulated ordering service, no ticket assignment, no leader election, and no storage emulation. But the abstract sequencing contract — a single total order of messages carrying sequence number, client id, client sequence number, reference sequence number, and minimum sequence number, together with each client's position in that order — is modeled, because without it most Container Runtime behavior cannot be stated at all.

DSL primer

What is a DSL?

A domain-specific language is a deliberately small language for one problem domain. SQL describes queries. Mermaid describes diagrams. This DSL describes Fluid collaboration scenarios.

A general TypeScript test can express almost anything. That flexibility creates incidental choices: loaders, callbacks, event wiring, queue timing, test harness helpers, and assertions can all be arranged in many ways. A DSL removes most of those choices and leaves a constrained vocabulary:

load attach disconnect submit operation sequence deliver synchronize summarize summary ack capture pending state resubmit expect

Why an internal DSL?

This is an internal DSL: TypeScript supplies the parser, module system, editor support, and type checker. There is no custom lexer or text parser. Progressive interfaces constrain which methods are legal at each point in the builder.

scenario name→source test→ document→clients→ coverage→steps

Three layers

Layer Responsibility File
Fluent grammar Readable authoring surface and compile-time ordering. builder.ts
Semantic model Pure commands, controls, expectations, and metadata. model.ts
Domain validator Deterministic errors phrased in Fluid concepts, plus trace invariants. validator.ts

The three orders

A Fluid scenario is a distributed execution, and its meaning lives in the gaps between three different orders. An ordinary test script collapses all three into JavaScript statement order and then hides the collapse behind a synchronization helper.

Order Owned by DSL verb What it decides
Submission order Each client's own runtime client(id).submitOperation / submitBatch / resubmitBatch What a client offered, and in what local order.
Sequence order The ordering service sequence().operations / chunk / summarize / summaryAck / join The single total order every client eventually agrees on.
Processing order and position Each client's delta queue service().deliver(id).through(pos), service().synchronize(...) How far each client has advanced through the total order.

Because the three are separate, the language can say things that were previously inexpressible: an operation is ordered while the client that must observe it is offline; two clients submit concurrently and the service picks a winner; a payload occupies three sequenced positions but reconstructs into one logical operation at the third; the same logical batch is submitted twice under two client identities and must still be applied once. 

s.concurrently((c) => {
  c.client("alice").submitOperation({ id: "alice-edit", dataStore: "root" });
  c.client("bob").submitOperation({ id: "bob-edit", dataStore: "root" });
});

// The service, not the statement above, decides the winner.
s.sequence().operations("seq-bob", "bob", ["bob-edit"]);
s.sequence().operations("seq-alice", "alice", ["alice-edit"]);
s.expectOrder("seq-bob", "seq-alice");
Sequence positions are symbolic names, never integers. The order of sequence() calls defines the sequence numbers. A scenario names only the positions it later refers to, and refers to them through referenceSequence, minimumSequence, pauseAt, deliver(...).through(...), expectOrder, and expectDelivery. Two names are reserved: baseline and latest.

Design lineage: Fowler and Tickloom

Martin Fowler's LLMs and DSLs article argues that a small language plus a deterministic validator narrows the space in which an LLM can make mistakes. The durable artifact becomes the domain program, not the prompt that generated it.

Tickloom demonstrates this with an internal Java DSL for distributed-system scenarios. Its strongest transferable ideas are:

  • progressive interfaces for grammar;
  • a semantic model separate from fluent syntax;
  • domain-level validation and execution;
  • scenario artifacts that are readable enough to maintain directly.

This Fluid design also corrects several Tickloom sharp edges:

  • Each client scope is immutable; selecting Bob cannot change an earlier Alice scope.
  • Commands are inspectable records, not anonymous execution lambdas. Tickloom's semanticmodel package still holds Action lambdas, process factories, and ClusterEvent.introduceIn(cluster), so its "semantic model" cannot be serialized, diffed, or analyzed without running it.
  • Persistent effects use honest verbs such as pause, resume, disconnect, and connect.
  • Identifiers and artifact provenance are validated before any future execution.
  • Ordering is declared, not coaxed. Tickloom nudges a simulated cluster with delays and partitions and then discovers the interleaving it produced; a scenario cannot state the interleaving it means. Here the interleaving is the artifact and the simulator is absent.

Tickloom's quorum and tick semantics are deliberately not borrowed. Fluid has a single ordering service and a dense total order, not a replicated log with per-replica clocks.

Scope and abstraction boundaries

In scope

  • container creation, attach, load, connect, disconnect, close;
  • intermediate connection states and requested connection mode;
  • DataStore creation, visibility, lazy realization, and opaque operations;
  • the abstract sequencing contract: one total order of sequenced messages carrying sequence number, client id, client sequence number, reference sequence number, and minimum sequence number;
  • protocol, summary, and DataStore message kinds as entries in that one order;
  • per-client delivery cursors, processing lag, and paused queues;
  • outbound batching and the logical-to-wire virtualization mapping;
  • pending state, replay, resubmission under a new client identity, and local acknowledgement;
  • summary generation, upload stage, broadcast, ack/nack, and handle reuse;
  • snapshot selection, refresh, and loading-group fetches;
  • ordinary pending-local-state capture and self-contained full-container capture;
  • frozen/offline writable load and later online resume.

Out of scope

  • DDS-specific operation semantics;
  • concrete driver implementations, endpoint names, token shapes, or cache internals;
  • any implementation of an ordering or storage service: no ticketing, no leader election, no server-side minimum-sequence computation, no snapshot storage emulation;
  • quorum proposal/accept/reject consensus;
  • deciding what a real service would have done with a given set of submissions;
  • full GC, aliasing, blob attach, staging mode, and signal APIs in the first prototype.
Do not confuse these two. "Do not model a concrete orderer" and "do not model ordering" are different statements. An earlier draft of this design conflated them and listed "a simulated ordering service" as out of scope in a way that read as "sequencing is out of scope." The result was a language that could not say that an operation was ordered while a peer was offline, could not distinguish submission from sequencing, and could not state that a replayed batch must be applied once. The abstract sequencing boundary is squarely in scope; only its implementation is not.
The DataStore/DDS boundary is intentional. A scenario may say that operation offline-3 targets DataStore root, but it does not say whether that operation is a map set, counter increment, tree edit, or sequence change. Container and protocol message kinds are not opaque in the same way, because batch markers, chunk markers, summary ops, and joins are exactly what the Container Runtime reasons about.

Fluid architecture represented by the language

Load pipeline

resolve URL→create document service→ connect storage→fetch snapshot/version→ initialize protocol→instantiate runtime→ replay saved/stashed ops→connect and catch up

Outbound operation pipeline

opaque DataStore op→ContainerRuntime submit→ Outbox batch→group→ compress→chunk→ Loader submitBatch→ordering service

Pending state stores the original unvirtualized runtime operations, including batch information and local metadata. That is why replay expectations use logical batch and operation identifiers rather than wire chunks. Resubmission assigns a fresh client sequence number and a fresh reference sequence number, which is why the DSL scopes client-sequence monotonicity to a connection epoch.

Inbound operation pipeline

sequenced message→unchunk→ decompress→unroll→ungroup→ batch classification→ duplicate batch detection→ pending-state reconciliation→ ContainerRuntime dispatch→ ChannelCollection→DataStore

Two facts from this pipeline shape the trace model. Grouping collapses a whole batch into one sequenced message, and ungrouping clones the outer message so every inner operation shares the outer sequence number while receiving a synthetic inner client sequence number. Chunking does the opposite: it spreads one payload across many sequenced messages, and only the final chunk carries the reconstructed payload, its original type, its metadata, and its compression marker. A boolean "chunked: true" cannot express either fact; a wire-message list can.

Batch identity and duplicate detection

explicit batchIdor derived clientId_[batchStartCsn]→ DuplicateBatchDetector→ discard repeat/DataCorruptionError

When a container rehydrates pending state under a new client identity, preserving the original batch identity is the only thing that lets peers reject the second copy. The DSL therefore treats a repeat as a declared duplicateOf relationship and rejects a replay whose identity does not match the original.

Summary pipeline

base validation→generate tree→ upload with context→submit summary op→ broadcast→ack or nack→ refresh tracked state/snapshot

States and transitions

Attach state

State Meaning Important transition
detached No service document yet. beginAttach or successful atomic attach.
attaching Create/attach is in progress. May be serialized; later completion becomes attached.
attached Backed by a service document or rehydrated attaching state. May connect, submit runtime ops, summarize, and capture pending state.

Serialization provenance matters: rehydrating state serialized while detached produces a detached container, while rehydrating state serialized while attaching produces an attached container.

Membership and catch-up

A client is catchingUp from the moment it obtains a connection until it has processed its own join message. Stating membership is opt-in per client: declare a join entry for a client and it passes through catchingUp; say nothing and connecting is a single step. A scenario pays for the precision only where it needs it. 

s.client("reader").load({ from: { kind: "service" } });
s.expectClient("reader").toBe({ connection: "catchingUp" });

s.sequence().join("seq-reader-join", "reader");
s.expectClient("reader").toBe({ connection: "connected" });
s.expectDelivery("reader").toBe({
  processedThrough: { relation: "equal", position: "seq-reader-join" },
});

The join carries three facts at once, matching connectionStateHandler.ts: the client is live from that position, it has processed everything ordered before it, and only from there can its own submissions be sequenced. A container whose inbound queue is paused stays catchingUp, because it has not processed its own join.

Losing a connection does not retire a membership; only a sequenced leave does. A reconnecting client therefore waits for its own leave before it is live again, and until then the retiring membership still pins the collaboration window at its old reference position. Because that leave often arrives after the replacement connection is established, it is legal as soon as the client is no longer connected.

Connection state is not connection mode

Axis Values Why separate?
Connection state disconnected, catchingUp, connected Describes the Loader connection and catch-up lifecycle.
Mode read, write A connected read client is not write-capable.
Read-only true, false Public/runtime read-only state is not identical to transport mode.
Environment none, service, frozen A writable frozen container can be logically connected without live driver wiring.

Operation states are relative to a client and a cursor

The five delivery states are mutually exclusive. Local optimistic application is checked separately with toBeAppliedTimes, so a locally applied operation can still be pending until it enters and returns through the trace.

State Meaning How the validator derives it
pending Offered by this client, not yet ordered. In the client's outstanding submission list.
sequenced Has a position this client has not reached. In the trace, beyond this client's processing cursor.
processed This client advanced through another client's operation. Cursor at or past the entry, with applied count at least one.
acked This client submitted it and processed its own sequenced copy. Cursor at or past the entry, with this client as submitter.
notProcessed Neither pending here nor present in the sequenced trace. No outstanding local submission and no sequenced position.

Local application is optimistic: a submitted operation takes effect at its submitter immediately, and processing its own sequenced copy is an acknowledgement rather than a second application. A container that loads at a position holds the effect of everything sequenced up to that position. Both rules are what make exactlyOnceApplication a meaningful claim across stash and replay.

Summary states and stages

Stages describe an attempt: base → generate → upload → submit. States describe its protocol lifecycle: local → broadcast → acked or nacked.

Captured state artifacts

Artifact Produced by Use
pendingLocalState IContainer.getPendingLocalState() Online resume with base snapshot, saved ops, and stashed runtime state.
fullContainerState captureFullContainerState() Self-contained frozen/offline load, including required attachment content.

These are not two modes of the same runtime method. They are separate current APIs with different guarantees. Full-container capture does not currently support loading groups.

The sequenced trace

A scenario's trace is the ordered list of sequence() entries recorded in its steps. The index of an entry is its sequence number; its name is how everything else refers to it.

Entry kinds

Kind Fluid counterpart Carries
operations MessageType.Operation carrying runtime ops Reconstructed logical operations, batch membership and markers, batch identity, virtualization.
operations with a non-final chunk ContainerMessageType.ChunkedOp Nothing. A non-final chunk reconstructs no logical operation.
join MessageType.ClientJoin The point a client becomes a live member, has processed everything ordered before it, and may have its own submissions sequenced.
leave MessageType.ClientLeave Retires a disconnected client, releasing the collaboration window it pinned.
noop MessageType.NoOp Moves a live client's reference position without carrying an operation.
summarize MessageType.Summarize The summary being broadcast, at the summarizer's reference position.
summaryAck MessageType.SummaryAck The summary op it answers and the snapshot handle it publishes.
summaryNack MessageType.SummaryNack The summary op it rejects and an optional retry delay.

Ordering metadata, symbolically

Wire field DSL form Default
sequenceNumber the entry's position in the trace assigned by declaration order
clientId client required, except for service-generated entries
clientSequenceNumber clientSequence omitted unless the scenario asserts something about it
referenceSequenceNumber referenceSequence: a position name or "baseline" the submitter's cursor when it offered the operation; the latest prior entry for a service-generated message
minimumSequenceNumber minimumSequence: a position name or "baseline" carried forward from the previous entry
metadata.batch batchPosition: single, start, continuation, end unmarked
metadata.batchId batchId derived client_[clientSequence]
grouping, compression, chunking virtualization none

One logical batch, three sequenced messages

s.client("writer").submitBatch({
  id: "large-batch",
  operations: [
    { id: "large-op-0", dataStore: "root", sizeInBytes: 100 },
    { id: "large-op-1", dataStore: "root", sizeInBytes: 100 },
    { id: "large-op-2", dataStore: "root", sizeInBytes: 100 },
  ],
});

s.sequence().chunk("seq-chunk-1", "writer", { batch: "large-batch", index: 1, count: 3 });
s.sequence().chunk("seq-chunk-2", "writer", { batch: "large-batch", index: 2, count: 3 });
s.sequence().operations("seq-chunk-3", "writer", [
  "large-op-0", "large-op-1", "large-op-2",
], {
  batch: "large-batch",
  virtualization: { grouped: true, compressed: true, chunk: { index: 3, count: 3 } },
});

s.service().deliver("reader").through("seq-chunk-2");
s.expectOperation("large-op-0").at("reader").toBe("notProcessed");

A reader holding two of three chunks has reconstructed nothing. That is what makes "reconnects while processing chunks" a real test and why the language needs a wire message concept rather than a boolean.

Replay must not apply twice

s.client("resumed").resubmitBatch({ batch: "edit-batch", as: "edit-batch-id" });
s.sequence().operations("seq-first-replay", "resumed", ["edit"], {
  batch: "edit-batch", batchPosition: "single", batchId: "edit-batch-id",
  clientSequence: 1, virtualization: { grouped: true },
});

// The client reconnects before it processed its own acknowledgement.
s.client("resumed").disconnect();
s.client("resumed").connect();
s.client("resumed").resubmitBatch({ batch: "edit-batch", as: "edit-batch-id" });
s.sequence().operations("seq-second-replay", "resumed", ["edit"], {
  batch: "edit-batch", batchPosition: "single", batchId: "edit-batch-id",
  clientSequence: 1, duplicateOf: "seq-first-replay",
  virtualization: { grouped: true },
});

s.expectOperation("edit").at("peer").toBeAppliedTimes(1);

Omit duplicateOf and the validator reports that the identity was already sequenced. Change the identity and it reports that a replay under a new client identity must preserve the original batch id, because otherwise no peer could reject the repeat.

Language grammar

Top-level form

fluidScenario("scenario name")
  .fromTest({
    file: "packages/test/test-end-to-end-tests/src/test/example.spec.ts",
    suite: "Suite name",
    test: "Test name",
  })
  .document(document("logical-document", dataStores, runtimeOptions))
  .clients(
    interactiveClient("alice"),
    summarizerClient("summarizer"),
  )
  .covers("op-stream", "summarization")
  .steps((s) => {
    // Scenario timeline
  });

Scopes

Scope Examples Semantic owner
s.client(id) load, attach, submit, resubmit, summarize, capture, realize, close Container/ContainerRuntime instance
s.concurrently(...) submissions with no relative order Several clients at once
s.sequence() operations, chunk, join, leave, noop, summarize, summaryAck, summaryNack The abstract sequencer: one total order
s.processing(id) pause or resume inbound/outbound processing Test-harness queue control
s.service() deliver, synchronize, completeAttach, full-container capture Abstract service/driver boundary
s.expect… client, operation, batch, summary, snapshot, delivery, order, convergence, trace, DataStore Observation checked against the declared trace

The verb tells you which order you are talking about

s.client("writer").submitOperation({ id: "edit", dataStore: "root" });  // submission
s.sequence().operations("seq-edit", "writer", ["edit"]);                // sequencing
s.service().deliver("reader").through("seq-edit");                      // processing

Nothing forces all three to happen, and that is the point. An operation can be submitted and never ordered; ordered and never delivered; delivered to one client and not another.

Immutable client scopes

const alice = s.client("alice");
const bob = s.client("bob");

alice.disconnect();
bob.submitOperation({ id: "op-1", dataStore: "root" });
alice.connect();

alice remains bound to Alice. Selecting Bob cannot mutate it. This avoids the shared-current-client bug identified in Tickloom's current builder.

Semantic model

Every fluent call appends a plain-data step. There are only three top-level step kinds:

  • command — an action or control stimulus;
  • expectation — a desired observation; the current proof-of-concept derives some, while the executor will be authoritative;
  • note — explanatory intent retained with the scenario.
{
  "kind": "command",
  "command": {
    "kind": "sequence",
    "entry": {
      "kind": "operations",
      "at": "seq-chunk-3",
      "client": "writer",
      "operations": ["large-op-0", "large-op-1", "large-op-2"],
      "batch": "large-batch",
      "virtualization": {
        "grouped": true,
        "compressed": true,
        "chunk": { "index": 3, "count": 3 }
      }
    }
  }
}

Because the IR contains no closures, loaders, containers, driver objects, or test provider instances, it can be serialized, diffed, rendered, analyzed, or consumed by a later executor. The trace is simply the ordered subsequence of sequence commands, so a scenario remains a single flat timeline.

Current validator and target ownership

The current validator.ts is a proof-of-concept combination of three responsibilities: structural scenario validation, trace checking, and semantic derivation. It never chooses an order, but it does replay the declared timeline and predict client and operation state. That made the domain precise before a real executor existed; it is not the intended permanent architecture.

Target responsibility split: fluent TypeScript types constrain the grammar; a scenario compiler checks IR integrity and produces an unambiguous execution plan; the real Fluid executor is authoritative for Loader and Runtime behavior; and an optional independent reference model predicts only selected stable contracts. See DEV.md for the maintainer specification.

Structural and lifecycle checks

  • unique client, DataStore, operation, batch, summary, snapshot, capture, and position names;
  • all references point to previously declared or produced artifacts;
  • load, attach, connect, disconnect, close, submit, summarize, and capture guards;
  • serialized detached/attaching provenance;
  • frozen load requires captureFullContainerState output;
  • compression requires grouped batching; chunking requires compression;
  • an explicit batch identity requires tracking derived from turn-based flushing and grouped batching, unless the disable gate is set;
  • loading groups require the loading-group snapshot-fetch feature gate;
  • writable frozen flow requires turn-based flush, grouped batching, and batch IDs;
  • full-container capture and loading groups are currently incompatible;
  • snapshot refresh adopts an existing acknowledged snapshot and never produces one.

Sequencing checks

  • a message only reaches the total order if its submitter is attached, service-backed, connected, and not behind a paused outbound queue;
  • a read-mode connection may hold pending local work but cannot place it in the total order until it transitions to write mode;
  • an entry may only carry operations its named client actually has outstanding;
  • a cursor only moves forward, never past a pinned position, never into a paused inbound queue, never on a disconnected or frozen container.

Trace invariants currently checked

Invariant What it rules out
denseTotalOrder Duplicate or unresolvable position names, reserved names used as positions.
clientSequenceMonotonic Client sequence numbers that stall or regress inside one connection.
batchContiguity Interleaved batches, mixed submitters, mixed reference positions, malformed begin/end markers.
causalReferenceSequence Referencing a position the submitter had not processed, or its own position.
minimumSequenceMonotonic A collaboration window that moves backwards, overtakes its submitter, or passes the least reference position among live write clients.
wireReconstruction Chunk runs with gaps, interleaving, or silent truncation.
exactlyOnceApplication A logical operation applied twice, including across replay under a new client identity.
orderedDelivery Rewound cursors and delivery a container could not have received.

Where invariants should ultimately live

An invariant may intentionally be checked at two boundaries because the declaration and the running implementation are different subjects. Dense order in the declared trace is structural: symbolic positions must be unique and the trace array is dense by construction. Dense sequence numbers emitted by Fluid are an executor conformance check. Likewise, explicitly authored client sequence numbers can be checked for monotonicity by the scenario compiler, while runtime assignment and reconnect resets must be observed by the executor.

Implementation-sensitive predictions such as collaboration-window behavior or exactly-once outcomes belong to the executor and, only when independent prediction earns its maintenance cost, the optional reference model. The complete invariant-ownership table is maintained in DEV.md.

Every invariant name is backed by a real check

expectTrace().toSatisfy([...]) is a checkpoint, not a comment. Some violations are accumulated while the timeline is replayed and attributed to the invariant they belong to; others are computed over the trace when the checkpoint runs. Naming a subset evaluates that subset at that point in the timeline, and a final sweep evaluates everything once, so nothing can hide by not being asked for. Each violation is reported once, at the step that caused it.

Derived expectations

Today the validator computes client state, operation states, application counts, delivery positions, batch virtualization, dispatch bunches, saved/stashed op counts, summary state, DataStore contents, and convergence. During the planned split, pure IR checks remain in the scenario compiler, actual Fluid behavior moves to the executor, and only selected high-value independent predictions move to the optional reference model. Snapshot fetch counts, summary tree/handle reuse, DataStore realization, and summary stage already require executor observation.

Bunches

Grouping puts a whole batch at one sequence position, and the Container Runtime then splits that message into contiguous runs before dispatch, starting a new run whenever the target DataStore changes. Returning to a DataStore after leaving it starts a new bunch; bunches are contiguous runs, not per-DataStore totals. 

s.expectBunches("seq-interleaved").toBe([
  { dataStore: "root", operations: ["root-0", "root-1"] },
  { dataStore: "secondary", operations: ["second-0"] },
  { dataStore: "root", operations: ["root-2"] },
]);

          it is sequenced but not processed here.
steps[9]: 'alice' is disconnected, so nothing it submitted can be sequenced

Worked example: disconnect gates inbound processing

export const disconnectGatesInboundOps = fluidScenario(
  "disconnect gates inbound operation processing",
)
  .fromTest({
    file: "packages/test/test-end-to-end-tests/src/test/container.spec.ts",
    suite: "Container",
    test: "can control op processing with connect() and disconnect()",
    lines: "374-447",
  })
  .document(document("collaboration", [{ id: "root", root: true }]))
  .clients(interactiveClient("writer"), interactiveClient("reader"))
  .covers("container-lifecycle", "op-stream", "op-ordering")
  .steps((s) => {
    s.client("writer").load({ from: { kind: "service" } });
    s.client("reader").load({ from: { kind: "service" } });
    s.expectClient("reader").toBe({ connection: "catchingUp" });
    s.sequence().join("seq-reader-join", "reader");
    s.expectClient("reader").toBe({ connection: "connected" });

    s.client("writer").submitOperation({ id: "initial-value", dataStore: "root" });
    s.sequence().operations("seq-initial", "writer", ["initial-value"]);
    s.service().synchronize();
    s.expectOperation("initial-value").at("reader").toBe("processed");

    s.client("reader").disconnect();
    s.expectClient("reader").toBe({ connection: "disconnected" });
    s.sequence().leave("seq-reader-leave", "reader");

    s.client("writer").submitOperation({
      id: "value-while-reader-disconnected",
      dataStore: "root",
    });
    s.sequence().operations("seq-while-disconnected", "writer", [
      "value-while-reader-disconnected",
    ]);
    s.note(
      "The operation is ordered by the service even though the reader is not " +
      "there to receive it. Sequencing and per-client processing are different events.",
    );
    s.service().deliver("writer").through("latest");
    s.expectOperation("value-while-reader-disconnected").at("writer").toBe("acked");
    s.expectOperation("value-while-reader-disconnected").at("reader").toBe("sequenced");
    s.expectDelivery("reader").toBe({
      processedThrough: { relation: "equal", position: "seq-initial" },
    });

    s.client("reader").connect();
    s.sequence().join("seq-reader-rejoin", "reader");
    s.expectOperation("value-while-reader-disconnected").at("reader").toBe("processed");
    s.expectDelivery("reader").toBe({
      processedThrough: { relation: "equal", position: "seq-reader-rejoin" },
    });
    s.service().synchronize();
    s.expectConvergence("writer", "reader");
    s.expectTrace().toSatisfy();
  });

What disappeared from the original test?

  • runtime factory construction;
  • provider plumbing;
  • entry-point casts;
  • DDS event and timeout wiring;
  • DDS value details.

What appeared that version 1 could not say

  • the operation reached the total order at position seq-while-disconnected while the reader was offline — previously the scenario could only say "synchronize the writer" and hope the reader stayed behind;
  • the reader's processing position is pinned at seq-initial, an assertion about a cursor rather than about a boolean;
  • the writer acked its own operation while the reader had not processed it, which is a statement about two different positions in one order;
  • the reader's membership: it is catchingUp until its own join is ordered, it leaves the collaboration when its connection drops, and rejoining is what carries it past the operation it missed;
  • the two clients converge at the end, which the validator checks by comparing cursors and applied-operation multisets.

Delete the final synchronize() and the validator reports three separate domain errors instead of silently passing.

5 Stashed ops with no saved ops offline/waitForSummary.spec.ts Saved and stashed counts derived from the cursor and the base position; replay under a new client identity applied once.
6 Writable frozen/offline round trip offline/frozenOfflineRoundTrip.spec.ts A frozen container cannot reach the sequencer at all; five offline ops become one grouped message on resume.
7 Older summarizer refreshes on the ack summarizationFetchValidation.spec.ts The summary ack is a sequenced entry; the trailing op exists only to pull cursors past it.
8 Detached serialize and rehydrate deRehydrateContainerTests.spec.ts An empty total order stated explicitly: both containers sit at the baseline position.
9 Incremental DataStore summaries summarizeIncrementally.spec.ts Handle reuse justified by the absence of any DataStore entry between two summary ops.
10 Loading-group offline refresh data-virtualization/groupIdOffline.spec.ts Snapshot refresh moves the base position forward while the cursor stays ahead of it; one grouped message dispatches as two per-DataStore bunches.

All definitions are in scenarios.ts, and each scenario carries its source file, suite, test name, line range, and coverage tags. fluidScenarioDsl.spec.ts adds focused positive and negative tests for explicit sequencing, submission versus sequencing, processing lag, replay and exactly-once application, wire reconstruction, ordering metadata, and summaries in the op stream.

Contributor workflow

Convert tests in two passes: first extract the behavior and distinguish it from harness mechanics, then attempt to express it with existing vocabulary. When a gap appears, prefer existing concepts, metadata on an existing event, or a new expectation before adding another command or trace-entry kind.

Every extension needs production evidence, a precise observable meaning, an owning layer, and tests at the component responsible for checking it. Structural IR integrity belongs to the scenario compiler. Actual Fluid behavior belongs to the executor. An independent reference-model prediction is optional and should exist only when differential testing justifies its synchronization cost.

The complete conversion workflow, expressibility-gap table, extension gate, and copy/paste How to convert an end-to-end test agent prompt live in DEV.md. They are maintained there rather than duplicated in this onboarding guide.

Evolution architecture and backlog

The DSL scenario remains the source of truth. Its plain IR should be compiled once into a normalized plan consumed by several independent components.

DSL types→IR→ scenario compiler→execution plan→ Fluid executor+TS renderer+ optional reference model

Runtime executor

The executor will drive real containers through ITestObjectProvider, observe the actual sequenced stream and client state, and evaluate expectations against Fluid. It will arrange test conditions and observe the ordering service; it will not simulate or choose the service's result.

  • map logical clients to real containers and entry points;
  • map opaque DataStore operations to a minimal test DataStore op source;
  • pause/resume/process inbound and outbound queues to realize the declared trace;
  • drive one client's cursor at a time to reproduce declared processing lag;
  • bind symbolic positions to observed sequenceNumber values and check the declared metadata against the observed message;
  • invoke summarizer helpers and observe summary ops and acks in the op stream;
  • wrap storage interfaces to count snapshot fetches;
  • capture and reload pending/full state artifacts;
  • evaluate expectation records and produce domain-level failures.

TypeScript reproduction renderer

The renderer will expand a failing plan into an explicit debuggable Mocha test with DSL step annotations, symbolic sequence names, harness calls, and captured trace state. Rendered files should normally be temporary files or CI artifacts rather than a second checked-in source of truth.

Optional reference model

A reference model is a small, pure, independent predictor for selected stable contracts. It does not drive Fluid or establish structural validity. It produces predicted observations that can be compared with executor observations for conformance and diagnosis, and it must not import the production algorithm it is checking. Scenarios remain executable when no reference-model rule applies.

Aspirational backlog

None of the following target components is implemented yet:

  • split the current validator into a structural scenario compiler and selected reference-model logic;
  • replace raw string cross-references with typed operation, submission, and sequence-position handles;
  • model DataStore attachment and reference edges without exposing DDS payload mechanics;
  • build the real Fluid executor and diagnostic TypeScript renderer;
  • add differential model-versus-runtime conformance scenarios;
  • run automated CI drift detection with trace and reproduction artifacts;
  • maintain rule ownership and production-symbol evidence;
  • support explicit compatibility profiles for intentional contract transitions.

DEV.md is the authoritative backlog with milestones and boundaries for each item.

Explicit limitations

These are boundaries of the current design, stated so that nobody mistakes silence for capability.

  • No quorum consensus. Membership is modeled through join and leave, but proposals, accepts, and rejects are not. The validator never computes a minimum sequence number for the scenario; it rejects a declared one that regresses, overtakes its submitter, or passes the least reference position among live write clients.
  • Bunching uses the DataStore boundary only. The Container Runtime also splits a bunch when the inner op type changes, and op types below the DataStore boundary stay opaque here.
  • No signals. Signals are not persisted, not replayed, and not ordered with respect to ops, so they need their own concept rather than a trace entry. They are not modeled.
  • Declarative observations remain. Snapshot fetch counts, summary tree/handle reuse, DataStore realization, and summary stage cannot be derived from the trace. They stay as recorded expectations for a future executor to check.
  • Replay-order expectations name batches. Loose pending operations are reported rather than silently dropped; wrap them in one-operation batches when the scenario needs to assert replay order.
  • Delayed delta connection is coarse. deltaConnection: "delayed" is represented as disconnected from the live stream; storage-based catch-up before connect() is not a separate delivery source yet.
  • Read-mode reconnect is coarse. A read connection cannot sequence pending work, and connect() models transition to write mode. The DSL does not yet express reconnecting explicitly in read mode.
  • No GC, aliasing, blob attach, or staging mode.
  • No DataStore reference graph. Visibility and opaque operations can describe some effects of storing a handle, but the source-to-target edge and DataStore attach message are not first-class yet.
  • No scenario-compiler split, executor, or reference model. The current validator still combines those concerns, and nothing runs the IR against ITestObjectProvider yet.

Glossary

Internal DSL
A domain language expressed through the syntax and type system of a host language.
Semantic model / IR
The plain-data representation produced by the fluent syntax.
Progressive interface
A builder interface that returns a narrower next interface, making invalid method orderings fail to compile.
Scenario compiler
The planned structural checker that validates IR references and provenance, then produces an unambiguous execution plan without predicting changing runtime logic.
Executor
The planned runner that drives real Fluid containers and treats their observed behavior as authoritative.
Reference model
An optional pure implementation of selected stable contracts, used to compare independent predictions with executor observations.
Artifact provenance
Information about how a snapshot or pending state was produced, used to validate legal future transitions.
Op virtualization
Container Runtime transformations that group, compress, and chunk logical runtime operations for transport, then reverse those transforms inbound.
Sequenced trace
The totally ordered list of sequenced messages a scenario declares. Its indices are the sequence numbers; its entries are named so that other parts of the scenario can refer to positions without writing integers.
Sequence position
A symbolic name for one entry in the total order, or one of the reserved names baseline and latest.
Processing cursor
How far one client has advanced through the total order. Two clients with different cursors are the DSL's model of processing lag.
Wire message
One entry in the total order. A grouped batch is one wire message carrying many logical operations; a chunked payload is many wire messages carrying one.
Batch identity
The value a peer uses to reject a repeated batch: an explicit batchId, or the derived clientId_[batchStartCsn].
Optimistic local application
A submitted operation takes effect at its submitter before the service orders it. Processing its own sequenced copy is an acknowledgement, not a second application.
Data virtualization
Lazy loading of DataStore snapshot content by loadingGroupId. It is distinct from op virtualization.
Saved op
A sequenced op after the base snapshot, replayed during pending-state load.
Stashed op
A local pending op applied at its original reference sequence and later resubmitted/reconciled.
